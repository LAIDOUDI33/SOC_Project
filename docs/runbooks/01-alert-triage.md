## Purpose and Scope

This runbook establishes standardized procedures for the initial triage of security alerts within the Djezzy National SOC Platform. It provides SOC analysts with a systematic approach to evaluate, classify, and prioritize incoming alerts from multiple security tools across the telecommunications infrastructure.

The scope encompasses:
- All alerts generated by the SIEM (Wazuh/Elasticsearch)
- EDR notifications (OSQuery/GRR integration)
- Network Security Monitoring (Suricata/Zeek/Arkime)
- Threat Intelligence feeds (MISP/OpenCTI)
- Telecom-specific fraud detection systems
- Vulnerability scanner findings (OpenVAS/DefectDojo)

## Severity Classification Framework

### P1 - Critical (Immediate Action Required)

**Definition:** Active compromise, data breach in progress, or imminent threat to critical infrastructure.

**Response Time:** < 15 minutes  
**Resolution Target:** < 4 hours

**Criteria:**
- Confirmed malware execution on production systems
- Active data exfiltration detected
- Privilege escalation to domain administrator
- Critical system unavailability affecting network operations
- DDoS attack impacting core services (>50% capacity reduction)
- ANRT-mandated reporting threshold events
- SIM swapping or subscriber data mass exposure
- Core network element compromise (HLR, MSC, SGSN)

**Examples:**
```
ALERT: Ransomware encryption activity detected on billing server X
ALERT: Unauthorized access to HLR database with admin credentials
ALERT: DDoS attack exceeding 100 Gbps targeting DNS infrastructure
```

### P2 - High (Urgent Response Required)

**Definition:** Significant security event requiring immediate investigation but no confirmed active compromise.

**Response Time:** < 30 minutes  
**Resolution Target:** < 8 hours

**Criteria:**
- Suspicious lateral movement patterns
- Multiple failed authentication attempts from external IPs
- Malware detection on non-critical systems
- Unusual data access patterns on customer databases
- Command and control communication indicators
- Phishing campaign targeting executive staff
- VPN anomalies or unauthorized remote access attempts
- Significant configuration drift on security controls

**Examples:**
```
ALERT: Brute force attack detected against LDAP directory (500+ attempts/hour)
ALERT: Potential C2 beaconing from workstation in Finance department
ALERT: Unusual bulk export of subscriber records from CRM system
```

### P3 - Medium (Standard Investigation)

**Definition:** Security event requiring investigation within normal operating hours.

**Response Time:** < 4 hours  
**Resolution Target:** < 24 hours

**Criteria:**
- Single host malware detection (contained/quarantined)
- Policy violations without clear malicious intent
- Minor vulnerability exploitations (low-risk assets)
- Suspicious but inconclusive behavioral anomalies
- Failed social engineering attempts
- Third-party vendor security concerns
- Non-critical system patching requirements

**Examples:**
```
ALERT: Outdated TLS configuration on internal web application
ALERT: Employee accessed resource outside normal business hours
ALERT: Single phishing email reported by user (no click-through)
```

### P4 - Low (Routine Processing)

**Definition:** Informational alerts requiring documentation and trend analysis.

**Response Time:** < 24 hours  
**Resolution Target:** < 72 hours

**Criteria:**
- Routine vulnerability scan results
- Informational security log entries
- Known benign false positive patterns
- Scheduled maintenance-related alerts
- Reputation-based low-confidence indicators
- Training and awareness opportunities

**Examples:**
```
ALERT: SSL certificate expiration warning (30 days)
ALERT: Routine port scan from known scanning service
ALERT: User password expiration notification
```

## Initial Response Procedures

### Step 1: Alert Acknowledgment (All Severities)

Upon receiving any alert, the analyst must:

1. **Acknowledge the alert** in the SOAR platform (TheHive) within SLA timeframes
2. **Record initial timestamp** of acknowledgment
3. **Assign preliminary severity** based on classification criteria
4. **Create case file** if not auto-generated

```bash
# Example: Acknowledge alert via API
curl -X POST https://soc-platform.djezzy.local/api/alerts/{alert_id}/acknowledge \
  -H "Authorization: Bearer $SOC_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "analyst_id": "analyst_username",
    "timestamp": "'$(date -Iseconds)'",
    "initial_severity": "P1"
  }'
```

### Step 2: Initial Data Collection

For each alert, collect the following information:

| Data Category | Sources | Collection Method |
|--------------|---------|-------------------|
| Alert Context | SIEM | Export full alert JSON |
| Raw Logs | Elasticsearch | Query relevant time window |
| Network Data | Zeek/Arkime | PCAP extraction for affected hosts |
| Endpoint Data | OSQuery/GRR | Live response if available |
| Threat Intel | MISP/OpenCTI | IOC correlation check |
| Asset Info | CMDB | Affected asset criticality |

### Step 3: Preliminary Assessment Questions

Answer these questions to guide triage:

1. **Is this a known false positive pattern?** → Check FP database
2. **Does this affect critical telecom infrastructure?** → Escalate if yes
3. **Is there evidence of active exploitation?** → Check EDR telemetry
4. **Are customer/subscriber data at risk?** → Immediate containment review
5. **Does this require regulatory notification?** → Consult compliance team
6. **Are there related alerts?** → Correlation search required

### Severity-Specific Initial Actions

#### P1 - Critical Immediate Actions

```
IMMEDIATE ACTION CHECKLIST:
□ Notify SOC Manager via emergency channel (SMS + PagerDuty)
□ Initiate Incident Bridge call (conference line: +213XXXXXXXXX)
□ Begin evidence preservation procedures
□ Activate incident command structure
□ Assess need for immediate containment (isolation)
□ Prepare ANRT notification template if applicable
□ Document all actions in real-time
□ Engage IR team members (on-call rotation)
```

#### P2 - High Priority Actions

```
HIGH PRIORITY ACTIONS:
□ Assign dedicated analyst for investigation
□ Enrich alert with additional context
□ Perform initial correlation analysis
□ Determine affected scope
□ Update stakeholder dashboard
□ Schedule follow-up review (2-hour interval)
□ Prepare escalation path if situation degrades
```

#### P3/P4 - Standard Actions

```
STANDARD PROCESSING:
□ Add to analyst queue for processing
□ Perform basic enrichment
□ Document findings in case notes
□ Schedule based on current workload
□ Close or escalate as appropriate
```

### ANRT Regulatory Escalation

Per Algerian telecommunications regulations, the following events require ANRT notification:

**Immediate Notification (within 4 hours):**
- Major service disruption affecting >10% of subscribers
- Suspected state-sponsored cyber attack
- Critical infrastructure compromise
- Mass subscriber data breach (>1000 records)

**Standard Notification (within 72 hours):**
- Confirmed data breaches of any size
- Significant security control failures
- Regulatory audit findings

## False Positive Identification

### Common False Positive Patterns

#### Network Security False Positives

| Pattern | Description | Mitigation |
|---------|-------------|------------|
| Internal Scanner Traffic | Vulnerability scanners, backup systems | Create exclusion rules for scanner IPs |
| Authorized Penetration Testing | Approved security assessments | Maintain testing calendar, tag test IPs |
| High-Bandwidth Legitimate Traffic | Software updates, CDN traffic | Whitelist known update servers |
| DNS Anomalies | New domains, high query volume | Tune thresholds, exclude CDNs |
| Protocol Misidentification | Custom telecom protocols | Update Suricata ruleset |

#### Endpoint Detection False Positives

| Pattern | Description | Mitigation |
|---------|-------------|------------|
| Administrative Tools | Remote administration software | Exclude approved admin tools |
| Legitimate Automation | IT automation, monitoring agents | Create exception policies |
| Development Activities | Build processes, testing environments | Segment dev networks separately |
| Approved Security Tools | Antivirus, DLP agents | Coordinate tool configurations |

#### Telecom-Specific False Positives

| Pattern | Description | Mitigation |
|---------|-------------|------------|
| SS7/SIGTRAN Signaling | Normal signaling traffic | Understand protocol baselines |
| Roaming Authentication | International roaming handoffs | Correlate with roaming partner list |
| Bulk SMS Campaigns | Marketing messages, OTPs | Register legitimate senders |
| Network Probes | Equipment health checks | Document probe sources |

### False Positive Handling Procedure

1. **Identify Pattern Match**
   - Compare alert characteristics against known FP signatures
   - Review historical similar alerts and their dispositions

2. **Validate Assumption**
   - Confirm with asset owner if uncertain
   - Verify against change management calendar
   - Cross-reference with approved activities

3. **Document Finding**
   ```json
   {
     "fp_classification": "authorized_scanner",
     "confidence": "high",
     "evidence": [
       "Source IP matches vulnerability scanner (192.168.10.50)",
       "Activity aligns with scheduled scan window",
       "No anomalous post-scan behavior observed"
     ],
     "recommended_action": "create_suppression_rule",
     "rule_suggestion": {
       "source_ip": "192.168.10.50",
       "destination": "any",
       "duration": "permanent",
       "reason": "Authorized Nessus Scanner"
     }
   }
   ```

4. **Implement Suppression**
   - Create exception rule in SIEM
   - Add to false positive knowledge base
   - Consider rule tuning if pattern is common

5. **Review Cycle**
   - Quarterly review of all suppression rules
   - Validate exceptions remain valid
   - Remove stale exceptions

### Tuning Recommendations

To reduce false positive rates while maintaining detection efficacy:

1. **Baseline Establishment**
   - Run in detection-only mode for 2 weeks before blocking
   - Establish per-environment baselines
   - Document expected behavior patterns

2. **Threshold Optimization**
   - Adjust count thresholds based on environment size
   - Implement time-based rate limiting
   - Use scoring models over binary decisions

3. **Contextual Enrichment**
   - Integrate asset criticality data
   - Include user behavior analytics
   - Apply threat intelligence context

## Triage Workflow

### Standard Triage Process Flow

```
┌─────────────────────────────────────────────────────────────────┐
│                    ALERT RECEIVED                                │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│              STEP 1: INITIAL ASSESSMENT                          │
│  • Acknowledge alert (< 5 min for P1/P2)                        │
│  • Extract key IOCs (IPs, hashes, domains)                      │
│  • Identify affected assets                                     │
│  • Check for duplicates/correlations                            │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│              STEP 2: ENRICHMENT                                  │
│  • Query threat intelligence platforms                          │
│  • Pull endpoint telemetry                                      │
│  • Retrieve network logs (PCAP if available)                    │
│  • Check user/activity context                                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│              STEP 3: CLASSIFICATION                              │
│  • Apply severity framework (P1-P4)                             │
│  • Determine incident type                                       │
│  • Assess scope and impact                                       │
│  • Identify false positive likelihood                            │
└──────────────────────────┬──────────────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
┌─────────────────────────┐  ┌─────────────────────────────────┐
│   TRUE POSITIVE PATH    │  │     FALSE POSITIVE PATH         │
│  • Escalate as needed   │  │  • Document FP pattern           │
│  • Initiate IR playbook │  │  • Create suppression rule      │
│  • Assign investigator  │  │  • Update knowledge base        │
│  • Notify stakeholders  │  │  • Close alert                   │
└─────────────────────────┘  └─────────────────────────────────┘
```

### Quick Reference Decision Tree

```
START
  │
  ├─ Is alert from trusted source with high confidence?
  │   └─ NO → Reduce priority, verify source integrity
  │   └─ YES → Continue
  │
  ├─ Does it affect CRITICAL infrastructure (HLR, Billing, Core)?
  │   └─ YES → Minimum P2, likely P1
  │   └─ NO → Continue
  │
  ├─ Is there evidence of ACTIVE exploitation?
  │   └─ YES → P1 or P2 based on scope
  │   └─ NO → Continue
  │
  ├─ Are subscriber/customer data involved?
  │   └─ YES → Elevate one severity level
  │   └─ NO → Continue
  │
  ├─ Is this a KNOWN false positive pattern?
  │   └─ YES → P4, document and close
  │   └─ NO → Continue
  │
  └─ Default classification based on remaining criteria
```

### Quick Query Templates

#### Elasticsearch Alert Search
```json
GET /alerts-*/_search
{
  "query": {
    "bool": {
      "must": [
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "term": { "status": "new" } }
      ]
    }
  },
  "sort": [{ "severity.level": "desc" }],
  "size": 50
}
```

#### Arkime Session Extraction
```bash
# Extract sessions for suspicious IP
curl -s "https://arkime.soc.djezzy.local/api/sessions?date=-1&expression=ip==1.2.3.4" \
  -H "Authorization: Bearer $ARKIME_TOKEN"
```

#### MISP IOC Lookup
```bash
# Search for IP in MISP
curl -s "https://misp.soc.djezzy.local/attributes/restSearch" \
  -H "Authorization: $MISP_KEY" \
  -H "Content-Type: application/json" \
  -d '{"value":"1.2.3.4","type":"ip-dst"}'
```

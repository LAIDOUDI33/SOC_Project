Chapter 1

Executive Overview & Architecture

The Djezzy National Security Operations Center (SOC) Platform represents a comprehensive, enterprise-grade solution designed specifically for telecommunications security operations. Built entirely on open-source technologies and deployed as a 100% on-premises solution, this platform integrates 39 microservices across 15 specialized security tools to provide complete visibility, detection, and response capabilities for one of Algeria's largest mobile network operators.

The architecture follows a modern containerized microservices pattern, utilizing Docker for service isolation and Kubernetes for orchestration at scale. Each security tool operates as an independent container with well-defined API interfaces, communicating through a centralized Apache Kafka event streaming backbone. This design ensures high availability, horizontal scalability, and the flexibility to upgrade or replace individual components without disrupting the entire system.

Disaster Recovery Site (8 Servers)

The DR site maintains a scaled-down but fully functional copy of the primary infrastructure, designed to take over operations within a defined RTO (Recovery Time Objective) of 4 hours and RPO (Recovery Point Objective) of 1 hour for critical data. The DR site operates in active-passive mode with continuous replication from the primary site via PostgreSQL logical replication and Kafka mirror maker.

⚠ Network Requirements
Minimum 10Gbps dedicated link required between primary and DR sites for replication traffic. For optimal performance during failover scenarios, a 40Gbps or 100Gbps dark fiber connection is strongly recommended.

Chapter 4

Step-by-Step Deployment Procedure

This chapter provides the complete step-by-step procedure for deploying the Djezzy SOC Platform from scratch. Follow these instructions in sequence to ensure a successful production deployment. Each step includes verification commands to confirm successful completion before proceeding to the next phase.

  1. Generate Secure Credentials

    Begin by generating all necessary API keys, passwords, and certificates required by the platform components. The included script creates cryptographically secure credentials and stores them in environment files.

    # Navigate to project directory cd /opt/djezzy-soc-platform # Generate secure credentials node scripts/generate-secure-credentials.js # Review generated credentials file cat .env.production.filled | head -30
  2. Deploy Infrastructure Layer

    Start the foundational services that all other components depend upon: PostgreSQL database, Redis cache, and PgBouncer connection pooler. These services must be fully operational before deploying security tools.

    # Start infrastructure services in order docker compose -f docker-compose.prod.yml up -d \ postgresql \ pgbouncer \ redis-master \ redis-replica-1 \ redis-replica-2 \ redis-sentinel-1 \ redis-sentinel-2 \ redis-sentinel-3 # Wait for PostgreSQL to be ready (health check) docker compose -f docker-compose.prod.yml logs -f postgresql | grep -q "database system is ready" # Initialize database schema docker compose -f docker-compose.prod.yml exec postgresql psql -U soc_user \ -d soc_production -f /docker-entrypoint-initdb.d/01-init-schema.sql
  3. Deploy Event Streaming Layer

    Initialize the Apache Kafka cluster with Zookeeper ensemble. Kafka serves as the central nervous system for event distribution between all security tools. A 3-broker configuration provides fault tolerance and horizontal scalability.

    # Start Zookeeper ensemble first (required by Kafka) docker compose -f docker-compose.prod.yml up -d \ zookeeper-0 zookeeper-1 zookeeper-2 # Verify Zookeeper is running for i in 0 1 2; do echo "Checking zookeeper-$i..." docker compose -f docker-compose.prod.yml exec zookeeper-$i \ zkServer.sh status | grep "Mode:" done # Start Kafka brokers docker compose -f docker-compose.prod.yml up -d kafka-0 kafka-1 kafka-2 # Create required topics docker compose -f docker-compose.prod.yml exec kafka-0 \ kafka-topics.sh --create --if-not-exists \ --topic soc.alerts --partitions 12 --replication-factor 3 \ --bootstrap-server localhost:9092 docker compose -f docker-compose.prod.yml exec kafka-0 \ kafka-topics.sh --create --if-not-exists \ --topic soc.events --partitions 24 --replication-factor 3 \ --bootstrap-server localhost:9092
  4. Deploy SIEM Stack (Wazuh + Elasticsearch)

    Deploy the Security Information and Event Management stack consisting of Wazuh Manager for correlation/alerting and Elasticsearch cluster for log storage and search. This forms the backbone of the platform's detection capabilities.

    # Deploy Elasticsearch cluster (3 nodes for HA) docker compose -f docker-compose.prod.yml up -d \ elasticsearch-node-1 elasticsearch-node-2 elasticsearch-node-3 # Wait for Elasticsearch cluster to form (green status) sleep 30 curl -k https://localhost:9200/_cluster/health?pretty # Deploy Wazuh components docker compose -f docker-compose.prod.yml up -d \ wazuh-indexer wazuh-manager wazuh-dashboard # Verify Wazuh API is accessible curl -k https://localhost:55000 -u admin:${WAZUH_PASSWORD}
  5. Deploy EDR Stack (GRR + Osquery Fleet)

    Deploy the Endpoint Detection and Response infrastructure including GRR Rapid Response for remote live forensics and Osquery Fleet for distributed endpoint querying. These tools enable deep visibility into endpoint activity across the organization.

    # Deploy GRR server docker compose -f docker-compose.prod.yml up -d grr-server # Deploy Osquery Fleet management console docker compose -f docker-compose.prod.yml up -d osquery-fleet # Initialize GRR administrative account docker compose -f docker-compose.prod.yml exec grr-server \ grr_config_updater initialize --external_hostname=grr.djezzy.local # Generate Osquery enrollment secret docker compose -f docker-compose.prod.yml exec osquery-fleet \ fleetctl setup --env-file /etc/fleet.env
  6. Deploy NSM Stack (Suricata + Zeek + Arkime)

    Deploy the Network Security Monitoring stack for real-time intrusion detection, protocol analysis, and full packet capture. Suricata provides IDS/IPS capabilities, Zeek performs deep protocol analysis, and Arkime enables PCAP visualization and search.

    # Deploy Suricata IDS/IPS (requires host networking) docker compose -f docker-compose.prod.yml up -d suricata # Deploy Zeek controller for protocol analysis docker compose -f docker-compose.prod.yml up -d zeek-controller zeek-worker-1 zeek-worker-2 # Deploy Arkime for PCAP visualization docker compose -f docker-compose.prod.yml up -d arkime # Configure Suricata to monitor production interfaces docker compose -f docker-compose.prod.yml exec suricata \ suricata-update update-rulesources docker compose -f docker-compose.prod.yml restart suricata
  7. Deploy SOAR Stack (TheHive + Cortex)

    Deploy the Security Orchestration, Automation and Response platform. TheHive provides case management and incident tracking while Cortex offers automated analysis through integrated analyzers for threat intelligence enrichment.

    # Deploy TheHive case management docker compose -f docker-compose.prod.yml up -d thehive cassandra elasticsearch-thehive # Deploy Cortex analysis engine docker compose -f docker-compose.prod.yml up -d cortex # Configure Cortex analyzers (VirusTotal, MISP, etc.) docker compose -f docker-compose.prod.yml exec cortex \ /opt/cortex/tools/add-analyzer.py VirusTotal_3 --auto-start true docker compose -f docker-compose.prod.yml exec cortex \ /opt/cortex/tools/add-analyzer.py MISP_3_1 --url http://misp:80 --key ${MISP_API_KEY}
  8. Deploy Threat Intelligence (MISP + OpenCTI)

    Deploy the threat intelligence platforms for IOC management and STIX-based threat analysis. MISP serves as the primary IoC sharing platform while OpenCTI provides advanced MITRE ATT&CK mapping and threat actor profiling.

    # Deploy MISP threat intelligence platform docker compose -f docker-compose.prod.yml up -d misp mysql-misp redis-misp # Initialize MISP administration docker compose -f docker-compose.prod.yml exec misp \ ./server/initMISP.sh # Deploy OpenCTI for advanced TI analytics docker compose -f docker-compose.prod.yml up -d opencti redis-opencti opencti-connector-worker # Configure OpenCTI data connectors docker compose -f docker-compose.prod.yml exec opencti-connector-worker \ python connectors/misp-feed.py --start
  9. Deploy Vulnerability Management (OpenVAS + DefectDojo)

    Deploy the vulnerability scanning and management infrastructure. OpenVAS/GVM provides automated vulnerability scanning while DefectDojo offers vulnerability lifecycle management, risk scoring, and compliance reporting.

    # Deploy OpenVAS vulnerability scanner docker compose -f docker-compose.prod.yml up -d openvas ospd-openvas gvmd gsad # Initialize OpenVAS (this takes ~15 minutes on first run) docker compose -f docker-compose.prod.yml exec openvas gvm-setup # Create initial scanning target curl -sSk -u "${OPENVAS_USERNAME}:${OPENVAS_PASSWORD}" \ -X POST https://openvas:9392/gmp -d '\ Djezzy Network Infrastructure\ 10.0.0.0/8\ '
  10. Deploy Main SOC Platform Application

    Finally, deploy the main Next.js application that serves as the unified dashboard and API gateway connecting all security tools. This application should be started last as it depends on all other services being operational.

    # Build the SOC platform image docker compose -f docker-compose.prod.yml build soc-platform # Deploy the main application docker compose -f docker-compose.prod.yml up -d soc-platform # Wait for health check to pass sleep 60 curl -s http://localhost:3000/api/health | jq . # Verify all integrations are connected curl -s http://localhost:3000/api/system | jq '.integrations'

Troubleshooting & Common Issues

This chapter addresses common deployment issues and their resolutions. Each problem includes symptoms, root cause analysis, and step-by-step remediation procedures based on real-world deployment experience.

⚠Issue: Container Startup Failures

Symptoms: Containers repeatedly restarting with exit code 137 or "OOMKilled" status.

Root Cause: Insufficient memory allocation or resource limits not configured for production workload.

Resolution:

  • Check container logs: docker compose logs [service]
  • Verify memory limits in docker-compose.prod.yml match server capacity
  • Increase memory reservation for Elasticsearch (minimum 8GB per node)
  • Enable swap on host system for burst scenarios
⚠Issue: Kafka Connection Timeouts

Symptoms: SOC Platform unable to connect to Kafka brokers, timeout errors in application logs.

Root Cause: Network segmentation between services or Zookeeper ensemble not fully initialized.

Resolution:

  • Verify all Zookeeper nodes are in "leader/follower" mode
  • Check Kafka broker advertised listeners configuration matches internal DNS
  • Validate network connectivity: nc -zv kafka-0 9092
  • Review firewall rules allow inter-container communication on port 9092
⚠Issue: Wazuh Agent Connection Refused

Symptoms: Agents showing as "never connected" in Wazuh dashboard, registration failures.

Root Cause: Incorrect agent configuration pointing to wrong manager IP/port or certificate validation failure.

Resolution:

  • Verify WAZUH_MANAGER environment variable in ossec.conf
  • Check agent SSL certificate is signed by correct CA
  • Confirm port 1514/1515 is accessible from agent network segment
  • Restart agents with debug logging enabled for detailed error information

Update & Upgrade Procedure

  1. Pre-Upgrade Backup

    Create full backups of all databases and configurations before initiating any upgrade procedure. Verify backup integrity by performing a test restore to a staging environment.

  2. Rolling Update Strategy

    For stateless services (SOC Platform, API Gateway), use Docker Compose's rolling update feature to deploy new versions with zero downtime. For stateful services (PostgreSQL, Kafka), perform sequential node updates with replication verification between each node.

  3. Post-Upgrade Verification

    After completing updates, execute the full verification suite from Chapter 6 to confirm all integrations are functioning correctly. Monitor system metrics for at least 24 hours after major version upgrades.
